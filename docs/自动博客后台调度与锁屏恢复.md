# 自动博客任务在设置页隐藏后暂停的原因与修复

## 原因

原实现由 `batch.js` 在设置页维护队列、活动标签页、超时定时器和站点切换倒计时。设置页进入后台并被节流、冻结或丢弃时，调度也停止。`visibilitychange` 和 `focus` 回调又会在切回设置页时集中执行超时检查和补充标签页，因此看起来像“切回来才突然继续”。

隐藏音频无法保证页面生命周期，更不能阻止整个操作系统睡眠。原 `openNextTab()` 虽然标为异步函数，却没有等待 `chrome.tabs.create()` 回调；并发计数仅在回调里增加，调度池可能在标签创建完成前继续申请新标签。

## 修复

- `batch-runner.js` 由后台 Service Worker 独占调度。页面仅发送开始、停止和立即切换指令，并订阅本地持久化快照。
- 队列、在途任务、发送标记、重试次数、待关闭标签页及明细持久化到 `chrome.storage.local`。后台被回收后，从磁盘恢复，不重新下发已发送任务。
- 所有状态变更串行执行，创建标签页前先预占名额，再等待创建完成。先建立可识别的扩展临时页面，再持久化 tabId 并导航，覆盖创建中途退出的情况。
- 活动任务使用后台短定时器及扩展 API 调用维持执行；30 秒 `chrome.alarms` 负责后台被回收后的兜底唤醒，并在 Worker 加载时重建。最低支持 Chrome 120。
- 任务期间申请 `chrome.power.requestKeepAwake('system')`，允许锁屏、熄屏，并阻止因空闲进入系统睡眠。完成或停止后释放。
- 发现超过 45 秒没有调度时，平移在途超时起点，避免唤醒瞬间同时超时重试。
- 每个目标的历史去重表、调试评论和推广配置在开始时冻结，站点切换由后台完成。
- 结果和历史日志由后台保存；数据库同步走旁路，离线时合并待同步快照，避免网络超时队列无限堆积。
- 浏览器重启或扩展重载后，旧 tabId 可能失效或被复用。旧在途项标为需确认的失败，剩余未开始项继续执行；不会对旧在途项自动重新发表评论。
- “继续处理”改为检查 `result === 'unstarted'`，不再用已预置的全量结果数组长度判断。

## 验证

执行 `pnpm test`，包含扩展加载、普通脚本作用域、页面快照桥接及后台回归测试。后台测试使用隔离的浏览器替身，不访问真实博客或发表评论。

真实环境验收：

1. 先停止旧版任务，再到 `chrome://extensions` 重新加载扩展并重新打开设置页；不要卸载扩展，以保留本地历史。
2. 从批次日志载入原批次，使用“继续处理”执行未开始项；需要重试失败项时再按目标选择重试。
3. 启动一个可核对的小批次，设置并发为 2，切到其他页面或关闭设置页。稍后重新打开，应显示后台实际进度，任务标签页数不超过 2。
4. 保持浏览器运行，正常锁屏或熄屏至少 10 分钟；解锁后核对完成数和日志。无需切回设置页触发执行。
5. 在扩展管理页停止 Service Worker，再等待闹钟或网页结果唤醒后台，核对已下发任务没有重复发送。
6. 执行中停止任务，确认任务标签页关闭，不再补充新标签；再次继续时只处理未开始项。

自动化测试已覆盖上述执行器行为，真实设备的锁屏、熄屏验收仍需在当前 Chrome/macOS 环境完成。

## 系统边界

合盖、手动系统睡眠、关机或浏览器退出时，扩展无法持续执行。闹钟不能唤醒正在睡眠的电脑；唤醒后由后台恢复。空闲睡眠保活与系统强制休眠的区别参见 [Chrome power 文档](https://developer.chrome.com/docs/extensions/reference/api/power)，闹钟行为参见 [Chrome alarms 文档](https://developer.chrome.com/docs/extensions/reference/api/alarms)。
